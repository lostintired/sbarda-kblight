# Design

## Context

См. `proposal.md`, раздел Why. Сейчас `LightSettings` хранит профиль и неглубоко копируется для очереди `TrayApp`; `LightBoxSettings` — неизменяемая запись. `LightState.From` непосредственно переводит выбранные яркости в байты. Все автоматические записи проходят через один рабочий поток, а `Program.ApplyOnce` использует тот же `Keyboard.Apply` отдельно. `OnApplied` принимает первичный профиль и недостающий Light box из прочитанного блока. Окно автоматически увеличивается по содержимому и пока не предусматривает ограничение высотой экрана.

Новые команды устройства не нужны: выключение обеих подсветок яркостью 0 уже доступно пользователю. Запись сохраняет прежний цикл чтение–изменение своих байтов–запись–сверка и ограничения модели. Рабочую установку не обновляем без отдельной просьбы.

## Goals / Non-Goals

**Goals:**
- Разделить сохранённый профиль и фактическое состояние, отправленное в устройство.
- Единообразно вычислять состояние в трее и разовых командах, включая повторы и ожидание очереди.
- Сделать расчёт времени воспроизводимо проверяемым без клавиатуры и изменения часов Windows.

**Non-Goals:**
- Отдельная служба, новые задачи Windows, пробуждение компьютера и хранение двух копий дневного профиля.
- Изменение транспортного протокола, набора управляемых байтов и существующих ограничений неизвестного Light box.

## Decisions

### 1. Сохранённые настройки остаются единственным профилем

В `LightSettings` добавить `Enabled = true`, `LightBoxEnabled = true` и неизменяемый объект `QuietHours` с `Enabled = false`, `Start = "23:00"`, `End = "09:00"`. Независимый `LightBoxEnabled` позволяет не создавать `LightBox` из значений по умолчанию до чтения устройства. Отсутствующий или null объект расписания нормализуется к выключенному; неверное время не сбрасывает весь файл.

Объект расписания заменяется целиком, как `LightBoxSettings`, поэтому снимок очереди не меняется при следующей правке окна. Нельзя сохранять эффективные нули поверх `Brightness`, `LightBox.Brightness`, режимов и цветов. `LastGoodBlock` по-прежнему содержит реальный блок, в том числе ночные нули; он не является источником дневной яркости после завершения первичного чтения.

Альтернатива — временно обнулять общий профиль и сохранять резервную копию — создаёт риск потери настроек при выходе и гонках очереди, поэтому отклонена.

### 2. Чистый расчёт политики и единая точка применения

Выделить в `src/LightingPolicy.cs` независимый от окна и HID расчёт интервала: строгое время HH:mm, переданное местное время, полуоткрытый интервал, переход через полночь, равные времена и ошибки формата. Результат содержит активность, время окончания, эффективные признаки выключения. Изменение яркости выполняется только при построении отправляемого `LightState`, не в общем профиле.

`Keyboard.Apply` получает актуальное время непосредственно перед попыткой применения после ожидания мьютекса устройства; один момент используется для всех интерфейсов этой попытки. Очередь хранит выбранный профиль, а не заранее замороженный ночной или дневной результат. Повторы заново рассчитывают политику. Так `--apply`, `--check`, ручное применение, запуск и восстановление после сна имеют общие правила.

Результат для трея должен возвращать и фактически применённую политику/яркости, чтобы строка состояния не строилась по дневному снимку запроса. Завершение устаревшего запроса не должно перекрывать статус более нового завершённого запроса; расчёт активности расписания в окне не выдаёт ожидающую запись за уже выполненную.

Альтернатива — обнулять снимок только в `RequestApply` — не покрывает разовые команды и устаревает в очереди или при повторах.

### 3. Таймер наблюдает время, но не пишет каждый тик

В `TrayApp` добавить таймер с интервалом 1 секунда: пересчитывать местное время и сравнивать активность с предыдущей. Только изменение активности ставит запрос сверки, с причиной начала или окончания тихих часов и до трёх попыток. Уже существующие события старта, сна, подключения и правки используют свои причины и повторы. Изменение интервала или его выключение применяется обычным запросом после правки; таймер не должен дублировать его. Таймер останавливается при выходе.

При переходе с заменой ожидающего запроса используется существующее объединение очереди. Каждый запрос пересчитывает время перед попыткой; уже начатая операция может закончиться, затем применяется более новая. Стабильный интервал не порождает HID-обмена или журнала. Перевод времени и часового пояса естественно обнаруживается ближайшим тиком; прошедшие во сне интервалы не проигрываются. Соответствующая подпись окна обновляется даже при отсутствии устройства.

Альтернатива — рассчитывать единственный таймер до следующей границы — требует отдельной обработки перевода часов. Постоянная запись раз в секунду излишня и отклонена.

Физическая проверка изменения часового пояса обнаружила, что `DateTime.Now` продолжает использовать кэш прежнего пояса процесса. Поэтому `LocalClock.Now` получает местное время непосредственно через Windows `GetLocalTime`; расчёт политики остаётся чистой функцией от переданного времени. Этот источник используется перед каждой попыткой, в таймере, окне и журнале, чтобы смена пояса учитывалась без перезапуска.

### 4. Сначала получить неизвестный профиль, затем выключать

При первом запуске сохраняется существующее правило чтения без записи. При недостающем `LightBox` первая операция не меняет его байты, `OnApplied` сохраняет исходный профиль. Если после получения профиля требуется ночное или ручное выключение, сразу ставится следующий запрос. Нельзя брать дневную яркость из блока, уже обнулённого политикой. Не создавать искусственный Light box из значений по умолчанию ради расписания. Защита от правки пользователем во время чтения сохраняется: явная правка имеет приоритет.

Разовые команды сохраняют своё ограничение: без `LightBox` в файле его байты не меняются, файл не дополняется. Это исключение явно описано в спеках и документации. На обычном обновлении расписание выключено, а трей получает Light box до его использования пользователем.

Альтернатива — всегда подставлять заводской Light box — нарушает миграцию и может потерять пользовательский цвет.

### 5. Окно редактирует профиль, статус сообщает о применении

Добавить два флажка и блок расписания по спекам. Ручное выключение делает параметры соответствующей подсветки недоступными, сохраняя показанную яркость; активность тихих часов не мешает готовить дневной профиль. Существующий режим Light box «Выключен» оставить для совместимости, ручной флажок не меняет этот режим автоматически.

Поля времени — 24-часовые, с минутной точностью; значения по умолчанию показываются и при отключённом расписании. Для равного времени выводится оговорённая подпись. Обеспечить ограничение рабочей областью экрана и прокрутку, проверить русский/английский, светлую/тёмную тему и масштаб 100/150/200%. Все новые тексты — парами в `Text.cs` и дельте interface-language.

Прежний статус сохраняется для обычной работы. Для успешного ночного выключения и ручного выключения используется новый статус из auto-apply. Сбой, неизвестная или отсутствующая клавиатура остаются видимыми; строка активных тихих часов в окне существует отдельно.

## Risks / Trade-offs

- [Раннее сохранение нулей вместо профиля] → Проверить файл до, во время и после ночи; отдельно проверить недостающий Light box и правку во время чтения.
- [Устаревший запрос включает свет ночью] → Пересчёт перед каждой попыткой, следующий запрос при переходе, проверки ожидания и повторов через границу.
- [Ложный успешный статус] → Использовать фактически применённое состояние результата, сохранять приоритет ошибок.
- [Окно выросло за границы экрана] → Ограничение рабочей областью и прокрутка; визуальная проверка при разных масштабах.
- [Трей закрыт или компьютер спит] → Расписание работает только при запущенном трее; явно указать в пользовательской документации.
- [Разовая команда не знает Light box] → Сохранить прежнюю гарантию неизменности байтов и файла, сначала запустить трей для получения профиля.

## Migration Plan

1. Старый файл читается без изменения прежних значений, новые выключатели разрешают свет, расписание выключено. Сохранять новые поля только при очередном штатном сохранении.
2. Проверить чистый расчёт времени небольшим консольным проверочным проектом без сторонних пакетов в `tools/LightingPolicyChecks`, который использует тот же файл расчёта. Проверки должны завершаться ненулевым кодом при нарушении границ или приоритета выключателей; они не заменяют проверку HID.
3. Выполнить сборку, строгую проверку OpenSpec и ручные сценарии из tasks.md с журналом и чтением блока. До опытов сохранить пользовательский файл и блок, закрыть sbarda.exe, исключить одновременную запись трея и kbtool. После опытов восстановить файл и выполнить `KbLight.exe --apply`.
4. Пользователь получает сборку для проверки. Установка, коммит, публикация и архивирование не являются частью этой стадии.

Откат — прежний exe и исходный файл настроек. Старый exe игнорирует новые поля и не выполняет расписание; если свет остался погашен, применять восстановленный дневной профиль старым `--apply`.
