## Context

Все тексты сейчас — русские строковые литералы, разбросанные по семи файлам: `SettingsForm.cs` (подписи окна), `TrayApp.cs` (меню, причины, строка состояния, окно ошибки автозапуска), `Keyboard.cs` (сообщения результата записи), `KeyboardModel.cs` (журнал и причины ошибок файла модели), `LightSettings.cs` (названия эффектов, описание для строки состояния), `Program.cs` (`NoSettings`), `SystemWatcher.cs`. Причины записи («запуск программы» и др.) — тоже литералы, и они же попадают в журнал. NuGet и ресурсы `.resx` не используются (ADR-005), сборка — один exe.

## Goals / Non-Goals

**Goals:**
- Все тексты в одном файле, русский и английский рядом — по нему видно, что ничего не забыто, и по нему сверяется таблица спеки.
- Русский вывод байт в байт как сейчас.

**Non-Goals:**
- Механизм для третьего языка (сателлитные сборки, файлы переводов).
- Перевод сообщений исключений .NET и Windows.

## Decisions

### Один статический класс `Text` с парами строк
`src/Text.cs`: `static bool Ru` вычисляется один раз; каждый текст — свойство или метод вида `public static string Exit => Ru ? "Выход" : "Exit";`, тексты с подстановкой — методы (`KeyboardUnknown(string id)`). Вызывающий код пишет `Text.Exit`.
- Альтернатива: `.resx` + `ResourceManager` + сателлитная сборка `ru`. Отклонена: при single-file publish сателлитные сборки встраиваются, но выбор идёт по `CurrentUICulture`, и `KBLIGHT_LANG` пришлось бы превращать в подмену культуры; вдобавок `.resx` неудобно сверять со спекой, а языков два.
- Альтернатива: словарь ключ → (ru, en). Отклонена: опечатка в ключе ловится только при запуске, а свойство — компилятором.

### Выбор языка
`KBLIGHT_LANG` (`ru`/`en`, без учёта регистра) → иначе `CultureInfo.CurrentUICulture.TwoLetterISOLanguageName == "ru"`. На Windows .NET берёт `CurrentUICulture` из языка интерфейса пользователя (`GetUserDefaultUILanguage`), а не из региональных форматов — это и нужно: язык меню Windows, а не формат дат. Значение считывается при первом обращении к `Text` и не меняется до выхода.
- `InvariantGlobalization` в `src/KbLight.csproj` не включён, так что `CurrentUICulture` отражает язык Windows.

### Причины записи
Причины остаются строками, которые передаются в очередь и пишутся в журнал, — но берутся из `Text` (`Text.ReasonStartup` и т. п.). `--apply` и `--check` — ключи, не переводятся. Код нигде не сравнивает причины между собой, так что перевод поведения не меняет.

### Названия эффектов
`Effect.KnownNames` становится парой словарей или словарём кодов в `(ru, en)`; `KnownName(id)` возвращает по `Text.Ru`. Поле `name` из файла модели по-прежнему имеет приоритет и не переводится.

### Описание состояния для журнала
`LightState.Describe` (`effect=… brightness=…`) не трогается — оно одинаково на обоих языках.

## Risks / Trade-offs

- [Пропущенный литерал останется русским в английском режиме] → после переноса `grep` по кириллице в `src/*.cs` вне `Text.cs` должен быть пуст (комментарии в коде и так английские); проверка — задача.
- [Английский текст длиннее русского и обрежется в окне] → окно на `TableLayoutPanel` с `AutoSize`; проверить глазами запуск с `KBLIGHT_LANG=en`.
- [Журнал смешанный, если пользователь сменил язык Windows] → допустимо: статусы и состояние одинаковы, разбирать можно.
- [`KBLIGHT_LANG` — ещё одна недокументированная ручка] → описать в README в разделе для продвинутых.
